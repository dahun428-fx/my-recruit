## 가장 먼저 고칠 5가지

### 1. 요약 첫 문단을 세 문장으로 분리

현재 첫 문단은 약 290자로, SSR 전환·BFF·데이터 책임·공통 컴포넌트·도메인 전이를 한 번에 설명한다. `판단했고`와 `판단하는 역할`도 반복된다.

현재 표현:

> PHP·jQuery 레거시의 Next.js SSR 전환을 리드하며 렌더링 경계를 직접 판단했고, 모놀리식 BE–FE 분리 전략의 일환으로 React 전용 집계·프록시 BFF를 Node.js(Express)로 신규 구축하며, 데이터 처리 책임을 어느 계층에 둘지 판단하는 역할로 SSR 전환에서 BFF 개발까지 담당 범위를 넓혀 왔습니다.

권장 표현:

> 6년차 프론트엔드 개발자로, PHP·jQuery 레거시의 Next.js 전환을 리드했습니다. 페이지 특성에 따라 SSR과 CSR의 경계를 설계하고, 모놀리식 서비스의 BE–FE 분리를 위해 Node.js(Express) BFF를 구축했습니다. 요금제·권한 정책과 같은 복잡한 요구사항을 Config-Driven UI와 공통 컴포넌트 구조로 구현해 왔습니다.

`정산·계약과 유사한`은 실제 정산·계약 경험처럼 보이게 할 위험이 있다. 직접 경험이 없는 상태이므로 `요금제·권한 정책과 같은`까지만 쓰는 편이 정확하다.

### 2. 마지막 요약 문단은 삭제하거나 직접적인 지원 적합성 문장으로 교체

현재 표현:

> 일본어 협업과 개발 표준 정착 경험은 일본 현지 조직과 직접 협업하고 AX 과제를 발굴·주도하는 글로벌 웹 플랫폼 팀의 업무 방식과 이어집니다.

`이어집니다`는 추상적이고 바로 앞 문단을 다시 설명한다. 삭제해도 정보 손실이 거의 없다. 꼭 유지한다면 다음처럼 직접 쓰는 편이 낫다.

> 일본 조직과 직접 협업하고 AX 과제를 주도해 온 경험을 바탕으로, 글로벌 웹 플랫폼의 개발 방식과 품질 기준을 함께 개선할 수 있습니다.

### 3. 공통 컴포넌트 항목을 세 덩어리로 분리

현재 문장은 공통/로컬 판정, 시각 회귀, 타입 계약, E2E, 기획 협업, Storybook 210개를 모두 담는다. 이력서에서 가장 중요한 JD 대응 근거인데 오히려 읽기 가장 어렵다.

권장 구조:

- 신규 화면 개발 시 컴포넌트를 팀 공통과 서비스 로컬로 구분하는 기준을 수립
- 공통 변경의 회귀를 Storybook, TypeScript 타입·빌드 검사, Playwright E2E로 검증
- Storybook 스토리 210개로 재사용 컴포넌트를 카탈로그화하고 기획 단계의 UI 확인에 활용

`디자인시스템급`은 계층형 디자인시스템을 구축했다는 인상을 줄 수 있다. JD 키워드는 잡지만 실제 확인된 범위는 평면형 공통 컴포넌트 체계이므로, 본문에서는 `재사용 컴포넌트 체계`가 더 안전하다.

### 4. 반복되는 리드·주도·직접·전환 표현을 줄이기

문서 전체에서 `리드` 14회, `직접` 16회, `전환` 39회, `설계` 19회, `구조` 18회가 반복된다. 오너십을 강조하려는 의도는 좋지만, 반복되면 자기평가처럼 보이고 실제 성과가 약해진다.

교정 원칙:

- 역할 문장에서는 `리드/주도`를 쓰고, 실행 문장에서는 구체적인 동사로 대체
- `직접 판단` → `SSR/CSR 기준을 정의`
- `전환을 주도` → `6인 팀의 마이그레이션 계획과 기술 의사결정을 담당`
- `구조를 설계` → 실제 산출물인 `BFF 구축`, `공통/로컬 기준 수립`, `회귀 게이트 편입`으로 표현

### 5. 9쪽을 4~5쪽 수준으로 줄이기

첫 페이지의 핵심 성과와 뒤의 경력기술서가 같은 내용을 반복한다. 6년차 지원자의 9쪽 문서는 기술 면접 자료로는 풍부하지만, 채용 담당자의 1차 스캔에는 부담이 크다.

권장 감축 순서:

1. 핵심 성과 4개는 유지하되 각 항목을 한 줄로 제한
2. 네이버웹툰 핵심 근거인 미스미, 공통 컴포넌트/AX, BFF 경험만 상세 유지
3. AI 챗봇은 FE 아키텍처와 Config-Driven UI 중심으로 축약
4. 삼성물산은 성능 진단과 결과 중심의 3개 불릿으로 축약
5. 경력 요약과 경력기술서 사이에서 중복되는 기술 스택·역할 문장 삭제

권장:

## 표현·표기 일관성

- 공식 채용 직무명에는 `프런트엔드`를 유지하더라도, 자기 서술에서는 `프론트엔드` 또는 `프런트엔드` 중 하나로 통일한다.
- `BE–FE`, `FE`, `프론트엔드`가 섞여 있다. 공간이 허용되는 첫 등장에서는 `백엔드–프론트엔드`로 풀어 쓰는 편이 읽기 쉽다.
- `code splitting`, `Lazy Loading`, `End-to-End`, `E2E`의 대소문자와 한글 병기를 통일한다.
- `구조 완성`은 강한 단정이다. 실제 범위에 맞춰 `구조 구축` 또는 `구조로 전환`을 우선한다.
- 기술 표의 `LangChain · RAG · VectorDB`는 주력 프로덕션 역량처럼 읽힐 수 있다. `AI/LLM 협업·학습`처럼 범위를 표시하거나, 네이버웹툰 JD와 직접 관련이 낮으므로 축소를 검토한다.

## 네이버웹툰 JD 관점의 강점

- Next.js SSR과 Node.js BFF 경험이 모두 있고, 단순 사용이 아니라 렌더링·데이터 책임 경계를 설명할 수 있다.
- 일본 본사 개발자와 일본어로 직접 협업한 경험이 라인망가·일본 조직 협업 신호와 매우 잘 맞는다.
- 공통 컴포넌트의 재사용 판단과 회귀 검증 경험이 필수 요건에 직접 대응한다.
- 레거시 전환, 성능 측정, 다국어, 코드 리뷰, 기술 공유, AI 도구 도입까지 JD 키워드 커버리지가 높다.
- 수치가 풍부하고 개인 기여와 팀 기여를 대체로 구분한다.

## 남는 리스크

- 정산·계약 직접 경험이 없다. `유사한 복잡성`을 주장하기보다 요금제·권한·기능 노출 정책을 실제 사례로 보여주는 편이 낫다.
- 계층형 디자인시스템, 버저닝, 서비스별 채택률 경험이 없다. `디자인시스템급`이라는 표현을 반복하면 면접에서 기대 수준을 과도하게 높인다.
- Canvas·WebGL·EPUB과 K8s 경험은 없다. 이력서에서 억지 대응하지 않은 현재 방향이 맞다.
- 콘텐츠 도메인 경험은 없지만 우대사항의 필수 조건은 아니다. 글로벌 B2B·다국어·일본 협업을 전이 가능한 근거로 두면 충분하다.
- 경력기술서 2의 기간이 다른 확정본과 불일치한다는 내부 기록이 있다. 제출 전 `2025.11~2026.02`와 `2026.01~2026.06` 중 실제 기간을 반드시 확정해야 한다.

## 최종 권고

현재 상태도 정직한 상향지원 문서로 제출 가능하지만, 그대로라면 좋은 경력을 어렵게 읽히게 만든다. 우선순위는 `요약 3문장화 → 공통 컴포넌트 장문 분리 → 미스미 장문 분리 → 중복 제거 → 4~5쪽 압축 → 기간 불일치 확인`이다. 새 키워드나 새 성과 추가는 그다음이다.
