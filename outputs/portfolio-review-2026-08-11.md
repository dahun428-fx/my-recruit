## Executive verdict

**판정: 핵심 주장 수정 전에는 외부 제출 불가(not ready).**

텍스트 자체의 채용담당자 관점 평가는 **84/100, advisory PASS(기준선 80)**다. 역할 확장 흐름이 잘 보이고, AI코치·비즈36.5의 문제→판단→기여 연결과 검증 도구를 통한 조직 영향이 특히 강하다. 다만 이 점수는 문구의 설득 잠재력에 대한 평가다. 현재 문서에는 역할 범위가 넓게 쓰였거나 근거 등록·시점 확인이 필요한 수치가 있어, 사실 무결성 기준상 그대로 제출할 수 없다.

채용담당자 세부 점수: 빠른 이해 22/25 · 포지셔닝 18/20 · 비기술 성과 18/25 · 기여/신뢰 13/15 · 문구 완성도 13/15.

## 유지할 강점

- 프론트엔드에서 풀스택과 AI 서비스 제품화로 확장된 성장 방향이 선명하다.
- AI코치는 SSE, 중지·재시도·재생성, Markdown→React 렌더링처럼 실제 구현 판단이 구체적이다.
- 비즈36.5는 9주, 108페이지, 82화면, 점진적 React 공존이라는 난도와 실행 범위가 강한 사례다. 범위 정의만 정확히 하면 가장 설득력 있는 프로젝트다.
- Playwright 배포 게이트, JSON 시나리오, 다중 viewport, 시각 회귀, LLM 검사기는 일반 기능 개발자와 구별되는 강한 소재다.
- 3,493명, 400발화 정상 출력 100%, Lighthouse 91, QA 3시간→30분, 컴포넌트 90분→15분, 운영 3명→1명 등 검증된 수치 자산이 풍부하다.

## Must fix — 외부 제출 전 필수

1. **표지의 세 서비스 총괄 표현을 역할별로 분리한다.**
   - 위치/문구: p1, `프론트엔드를 총괄한 세 서비스`
   - 문제: AI코치 FE 리드, 비즈36.5 풀스택 내재화, 바이오에이지 인수·운영 개선은 역할 성격과 범위가 다르다. 현재 문구는 바이오에이지까지 동일한 총괄 역할로 읽혀 과장 위험이 있다.
   - 방향: 세 프로젝트를 각각의 확인된 역할로 병렬 제시한다. 포괄 동사는 `총괄`보다 각 프로젝트의 실제 책임을 드러내는 표현으로 바꾼다.

2. **비즈36.5의 단독 수행 범위와 기술 기여를 분리한다.**
   - 위치/문구: p4, `108 pages / 82 screens / 9 weeks / solo`, `풀스택 단독 수행(데이터 모델~화면)`, Node.js
   - 문제: 108페이지·82화면 전환과 신규 건강관리 기능의 End-to-End 수행은 확인됐지만, Node.js BFF는 팀 작업이다. 수치 간 관계와 `단독`이 가리키는 범위도 한 문장 안에서 불명확하다.
   - 방향: `전환 규모`, `전환 기간`, `단독 수행 범위`, `팀 기여 범위`를 별도 문장으로 나눈다. Node.js는 팀 기여로 표시하고, 108페이지와 82화면의 집계 기준을 정의한다.

3. **근거 등록 또는 정의가 없는 수치를 삭제·완화한다.**
   - p2 `AI 응답 평균 2초대`: metric registry에 없고 첫 청크·첫 토큰·전체 응답 중 무엇인지 불명확하다. 삭제하거나 측정 정의와 근거를 확인해 등록한다. 대체가 필요하면 검증된 `답변 출력 10초→4초`를 우선 검토한다.
   - p2 `12개 도메인 모듈`: 사용자 진술은 있으나 문서 근거와 metric registry 등록이 없다. 확인 전에는 `다수의 도메인 모듈`처럼 완화한다.
   - p8 `팀 10명 전원`: 사용자 진술은 있으나 문서 근거와 metric registry 등록이 없다. 확인 전에는 `팀 전체`로 완화한다.

4. **바이오에이지의 기간과 성과 표현을 사실 범위로 좁힌다.**
   - p7 `2025 ~ 재직중`: 근거는 2025년 수행까지만 확인된다. `2025`로 고치거나 현재 유지보수 여부를 확인해 증거를 추가한다.
   - p7 `UI와 데이터 운영 리스크를 걷어냈고`, `93/112 안정적으로 전환`: 무엇을 어떻게 바꿨고 무엇을 성공으로 판단했는지가 없다. 구체적인 문제·조치·성공 기준을 근거로 보강하거나, 확인된 `112곳 중 93곳 전환` 수준의 중립적 사실로 제한한다.

5. **테스트·더미 데이터 단정을 확인한다.**
   - 위치/문구: p1, `전부 테스트 계정·더미 데이터`
   - 문제: 텍스트 검토만으로 모든 화면을 확인할 수 없다.
   - 방향: 소유자가 전체 화면을 직접 점검해 사실임을 확인한다. 확인 전에는 `일부 화면은 테스트 계정·더미 데이터`처럼 범위를 좁힌다.

## Should fix — 설득력과 신뢰도 개선

1. **포트폴리오의 시간 범위를 밝힌다.** 총 경력 `5년 10개월`은 `2026-08 기준`을 붙이고, 본문은 전체 경력 중 최근 대웅제약의 2025년 이후 사례를 중심으로 구성했다는 점을 명시한다.
2. **헤드라인을 증거 범위에 맞춘다.** `AI까지`보다 `AI 서비스 제품화까지`처럼 실제 역할 확장을 구체화한다.
3. **AI코치 장문을 재구성한다.** 기능 나열 대신 `문제 → 핵심 판단 → 본인 기여 → 검증 결과` 순서로 나눈다. 이미 확인된 구현과 수치를 사용한다.
4. **병원 검색 사례에 판단과 결과를 추가하거나 비중을 낮춘다.** 현재는 UI 흐름 설명에 가까워 본인의 문제 해결과 결과가 드러나지 않는다.
5. **바이오에이지를 가장 먼저 보강한다.** 현재 가장 약한 사례다. 추상적 `인수·개선`보다 실제 문제, 본인 조치, 전환 성공 기준이 필요하다.
6. **검증 도구와 성과를 일대일로 연결한다.** p8~9에서 설정 빌더와 테스트 하네스를 분리하고, 각 도구가 QA 3시간→30분, 컴포넌트 90분→15분, 운영 3명→1명 중 어떤 변화에 기여했는지 명시한다. 검증된 범위를 넘는 인과는 만들지 않는다.
7. **과장될 수 있는 세부 표현을 완화한다.** p8~9의 `바로 확인`, `세션 주입/업로드`는 근거가 확인되지 않았다. 확인 가능한 동작 수준으로 바꾼다. p5의 GNB도 전체 108페이지 IA를 포괄한다는 매핑이 없다면 `주요 IA` 수준으로 좁힌다.
8. **캡션을 증거 문장으로 바꾼다.** `화면 다양성`, `실행 화면`, 반복되는 `반응형` 같은 설명 대신 `문제 / 변경 / 의미` 중 하나를 전달하도록 한다. 실행 전 상태라면 실행 결과처럼 쓰지 않는다.

## Could improve — 선택적 정교화

- `AX`, `Baseline`, `multi viewport`, `session injection` 같은 용어는 비기술 채용담당자가 이해할 수 있도록 한 줄로 풀어 쓴다.
- 프로젝트마다 `Problem / Decision·Contribution / Result` 구조를 통일하면 스캔 속도가 빨라진다.
- 반응형 관련 반복 문구는 하나의 검증 판단으로 합치고, 마이그레이션 경계와 검증 방법을 더 강조한다.
- 추상적 캡션은 제거하거나 구체적인 관찰 사실로 대체한다.

## 구체적인 재작성 방향

- 표지는 하나의 큰 역할로 묶지 말고 `AI코치—FE 리드`, `비즈36.5—풀스택 내재화`, `바이오에이지—인수·운영 개선`처럼 서로 다른 책임을 드러낸다.
- 프로젝트 본문은 `상황/문제 1문장 → 선택과 이유 1~2문장 → 내가 한 일 2~3문장 → 검증된 결과 1문장`으로 압축한다.
- 수치는 단독 배지처럼 두지 말고 반드시 대상·기간·측정 기준과 연결한다.
- `총괄`, `안정적으로`, `리스크를 걷어냈다`, `바로` 같은 강한 표현은 구체 근거가 있을 때만 유지한다.
- 신규 사실은 만들지 않는다. 근거가 없는 항목은 삭제·완화하거나 `[확인 필요]` 상태로 별도 관리한다.
