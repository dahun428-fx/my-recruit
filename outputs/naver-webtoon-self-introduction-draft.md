# 네이버웹툰 Frontend Developer 자기소개서 초안

## 1. 지원 동기와 경력

저는 프론트엔드에서 출발해 복잡한 요구를 화면 구조와 제품 아키텍처로 바꾸는 일을 해왔습니다. 한국미스미에서는 일본 본사 개발자와 일본어로 협업하며 글로벌 B2B 커머스의 한국 웹을 PHP·jQuery에서 Next.js·React·TypeScript로 전환했습니다. 대웅제약에서는 AI 건강검진 챗봇의 프론트엔드를 총괄하며 SSE 스트리밍, Markdown·표·차트·링크 렌더링, 오류 복구 흐름을 설계했고, 고객사별 테마와 기능 노출을 설정으로 제어하는 SaaS 구조까지 확장했습니다.

네이버웹툰 팀이 다루는 문제 중에서는 웹툰CONNECT의 원고 관리·정산·계약처럼 복잡한 B2B 정책을 직관적인 UX로 모델링하는 일에 가장 끌렸습니다. 저는 기능별 차등 과금이라는 비즈니스 요구를 고객사별 테마와 기능 노출을 설정으로 제어하는 Config-Driven UI로 바꾸고, 운영·기획 담당자가 코드 수정 없이 정책을 관리하도록 만든 경험이 있습니다. 서로 다른 역할과 정책이 얽힌 문제를 사용자가 이해하기 쉬운 화면과 변경 가능한 구조로 푸는 일에서 가장 직접적으로 기여할 수 있다고 생각했습니다.

라인망가와 같은 다국어·다지역 서비스를 일본 조직과 함께 운영하는 환경도 매력적입니다. 한국미스미의 글로벌 B2B 커머스를 전환할 때 일본 본사 개발자와 일본어로 직접 소통하며 한국 웹의 요구사항을 조율한 경험을 더 큰 글로벌 서비스에서 확장하고 싶습니다. 콘텐츠 뷰어는 새롭게 도전하고 싶은 영역입니다. EPUB·Canvas·WebGL 실무 경험은 없지만, SSE로 전달되는 비정형 LLM 응답을 Markdown·표·차트·링크로 안전하게 렌더링하고 실패 상태의 복구 흐름까지 설계한 경험을 바탕으로 전용 콘텐츠 렌더링 영역까지 역량을 넓히고 싶습니다.

입사 후에는 React·Next.js 기반의 렌더링 구조와 공통 컴포넌트를 견고하게 만들고, 성능 지표와 오류 데이터를 기준으로 개선을 반복하겠습니다. 콘텐츠를 보는 사용자와 이를 운영하는 파트너 모두가 복잡성을 의식하지 않아도 되는 프론트엔드를 만드는 데 기여하고 싶습니다.

## 2. 기술적으로 가장 어려웠던 문제

가장 어려웠던 문제는 목업 수준의 AI 건강검진 챗봇에서 형식과 품질이 매번 다른 LLM 응답을 실서비스 수준의 화면으로 만드는 일이었습니다. 저는 프론트엔드 총괄로서 아키텍처 분석·설계부터 구현과 테스트까지 맡았습니다. 문제를 단순한 채팅 UI 구현이 아니라, “응답이 지연되거나 일부만 도착하고 형식이 깨져도 사용자가 안전하게 읽고 복구할 수 있어야 한다”는 렌더링 신뢰성 문제로 정의했습니다.

먼저 AI 개발자와 응답 형식·스트리밍 방식·오류 정책을 합의하고, SSE 기반 실시간 렌더링과 중지·재시도·재생성 흐름을 구현했습니다. Markdown 응답은 전용 렌더링 계층에서 표·목록·링크·차트를 React 컴포넌트로 변환했습니다. XSS와 HTTP·LLM 오류를 유형별로 분리하고, 실패 유형에 따라 대체 UI와 재시도 경로를 제공했습니다.

기존처럼 전체 답변이 완성된 뒤 한 번에 출력하는 방식은 구현이 단순하지만 사용자가 약 10초 동안 결과를 기다려야 하고, 생성 중단이나 부분 실패에 대응하기 어려워 선택하지 않았습니다. 응답을 가공 없이 직접 표시하는 방식도 검토했지만, 표·링크·차트의 일관된 표현과 XSS 방어를 보장하기 어려워 전용 렌더링 계층을 택했습니다.

그 결과 답변 출력 시간을 10초에서 4초로 줄였고, 임직원 3,493명이 사용하는 서비스로 전환했습니다. 400건의 발화 검증 범위에서는 답변 화면 정상 출력률 100%를 확인했습니다. 이 경험을 통해 콘텐츠 렌더링의 품질은 정상 응답을 빠르게 보여주는 것뿐 아니라, 불완전한 입력과 실패 상황에서도 사용자가 다음 행동을 선택할 수 있게 만드는 데서 결정된다는 점을 배웠습니다.

## 3. 협업 중 불확실한 요구사항을 해결한 경험

AI 건강검진 챗봇의 핵심 기능을 완성한 뒤 고객사별 기능 차등 과금과 테마 변경 요구가 추가됐습니다. 당시에는 고객사마다 무엇이 달라져야 하는지, 변경을 개발팀과 운영팀 중 누가 관리할지 기준이 명확하지 않았습니다. 이미 완성된 화면에 조건문을 계속 추가하면 단기 일정은 지킬 수 있지만, 고객사가 늘수록 정책 충돌과 회귀 위험이 커지는 상황이었습니다.

저는 프론트엔드 총괄로서 기획·운영 담당자와 요구를 다시 나누었습니다. 고객사별로 바뀌는 테마와 기능 노출은 설정으로 관리하고, 모든 고객사에서 동일해야 하는 동작은 공통 코드에 남기는 기준을 세웠습니다. 이후 완성된 코드베이스를 Base-Theme과 Config-Driven UI 구조로 리팩토링해 운영·기획 담당자가 코드 수정 없이 고객사별 테마와 기능을 제어할 수 있도록 했습니다. 단기적으로는 리팩토링 비용이 컸지만, 조건문을 누적하는 대안보다 변경 책임과 검증 범위가 명확해지는 구조를 선택했습니다.

그 결과 최초 프론트엔드 구현에는 10주가 걸렸지만, 이후 신규 고객사 커스터마이징은 2주 만에 납품할 수 있었습니다. 이 경험을 통해 요구사항이 불확실할수록 개발자가 구현안을 먼저 방어하기보다, 누가 무엇을 언제 바꿀 것인지까지 함께 정의해야 한다는 점을 배웠습니다. 협업에서 제 역할은 의견을 한쪽으로 밀어붙이는 것이 아니라, 서로 다른 요구를 반복 가능한 제품 규칙과 검증 가능한 구조로 바꾸는 것이라고 생각합니다.

## 4. AI 도구로 개발 생산성과 팀의 일하는 방식을 개선한 경험

Codex와 Claude Code를 실무에 도입하면서 가장 먼저 본 문제는 코드 생성 속도가 아니라 결과의 편차였습니다. 사람마다 다른 컨텍스트와 검증 방법을 사용하면 빠르게 만든 코드라도 팀이 신뢰하기 어렵고, 담당자가 바뀌었을 때 같은 품질을 재현하기 어려웠습니다.

저는 컨텍스트 관리, 금지 패턴, 보안 위험, 필수 검증 절차를 포함한 FE AX 개발 표준을 단독 설계해 사내 공식 문서로 정착시켰습니다. 발화 테스트·LLM 응답 검증·타입 검사·빌드·배포 전후 확인을 자동 실행하는 검증 하네스를 만들고, Playwright E2E를 배포 파이프라인의 필수 게이트로 편입했습니다. 또한 Storybook 스토리 210개로 공통 컴포넌트를 카탈로그화하고, 개발 세미나 12회와 기술 문서 48건으로 사용법보다 판단 기준을 공유했습니다.

이 방식은 10명 스쿼드 전원의 개발 과정에 적용됐습니다. 반복 QA 시간은 3시간에서 30분으로, 반복 컴포넌트 개발은 90분에서 15분으로 줄었고, Storybook으로 UI를 조기에 확인하면서 기획·개발 검증 리드타임도 2일에서 1일로 단축했습니다. AI 도구의 가치는 개인이 코드를 빨리 만드는 데서 끝나지 않고, 팀이 같은 기준으로 생성 결과를 검증하고 재사용할 수 있을 때 커진다고 생각합니다. 네이버웹툰에서도 AX 과제를 발굴하는 데 그치지 않고, 코드리뷰·테스트·문서화까지 연결해 지속 가능한 팀의 개발 방식으로 만들겠습니다.
