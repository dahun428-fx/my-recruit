# 자기소개서 초안 평가 및 피드백

검토 기준:

- `outputs/base-resume.pdf`의 포지셔닝과 사실 범위
- `docs/resume-reference/metric-registry.md`의 수치 상태
- `docs/resume-reference/experience-bank.md`의 경험 근거
- 프로젝트의 자기소개서 작성 원칙과 개인 선호 규칙

## 결론

현재 원고는 소재가 부족한 초안이 아니라, 좋은 소재를 너무 많이 반복해서
핵심이 흐려진 초안입니다. 다섯 글을 하나의 자기소개서로 제출하면 같은 경력이
관점만 바뀐 채 반복되어 이력서의 장문 해설처럼 읽힙니다.

가장 좋은 방향은 다음과 같습니다.

1. 첫 번째 글의 **Product Engineer 포지셔닝**을 전체 자기소개서의 뼈대로
   사용합니다.
2. 다섯 번째 글의 **AI 코딩 에이전트 검증 체계와 팀 AX 전환**을 차별화
   사례로 결합합니다.
3. 세 번째 글의 **8초 → 2초 성능 개선**은 사용자 경험 문항이 있을 때만
   별도 답변으로 사용합니다.
4. 두 번째와 네 번째 글은 현재 근거가 확인되지 않는 사례를 제거한 뒤,
   문제 해결 또는 협업 문항용 답변 은행으로 남깁니다.

즉, “제품을 만들고 운영하는 사람”과 “팀이 반복해서 잘 만들 수 있는 기준을
설계한 사람”이라는 두 축만 남기는 것이 가장 강합니다.

## 전체 평가

| 항목 | 평가 | 피드백 |
| --- | --- | --- |
| 직무 정체성 | 좋음 | Product Engineer, 프론트엔드, AI 생산성 리드가 혼재합니다. 최종 명칭은 `프론트엔드에서 풀스택·AI까지 확장한 Product Engineer`로 통일하는 편이 좋습니다. |
| 경험의 질 | 매우 좋음 | AI 챗봇 제품화, 레거시 내재화, 성능 개선, 팀 AX 전환 모두 강한 소재입니다. |
| 근거와 수치 | 보완 필요 | 검증된 수치도 표현 범위가 넓어졌고, 근거 은행에서 확인되지 않는 사례가 여러 개 있습니다. |
| 차별성 | 좋음 | AI 서비스 제품화와 하네스 엔지니어링은 일반 프론트엔드 지원자와 분명히 구분됩니다. |
| 가독성 | 보완 필요 | 각 글이 5~6개 문단이고 문단마다 기술과 성과가 여러 개 들어가 핵심 장면이 남지 않습니다. |
| 지원 적합성 | 판단 보류 | 대상 회사, JD, 실제 문항, 글자 수가 없어 “왜 이 회사인가”와 입사 후 기여를 평가할 수 없습니다. |

현재 단계의 권장 판정은 **좋은 답변 재료, 제출 전 재구성 필요**입니다.

## 가장 먼저 고칠 점

### 1. 다섯 글을 한 문서로 합치지 않기

다섯 글 모두 다음 패턴을 반복합니다.

- 기능 구현에 머무르지 않는다는 선언
- AI 챗봇 또는 Next.js 사례
- 구조·체계·기반을 만들었다는 설명
- 앞으로도 같은 방식으로 기여하겠다는 결론

채용 담당자는 두 번째 글부터 이미 읽은 내용을 다시 읽는다고 느끼게 됩니다.
하나의 자유 형식 자기소개서라면 사례는 두 개면 충분합니다.

- 대표 제품 사례: AI 건강검진 챗봇 제품화
- 차별화 사례: 팀 AX 전환과 검증 하네스

나머지는 문항별 답변 은행으로 분리하는 편이 좋습니다.

### 2. 추상어보다 장면과 결과를 앞세우기

`구조`, `체계`, `기반`, `흐름`, `완성도`, `생산성`이 반복됩니다. 의미는
좋지만 구체적인 행위 없이 연달아 쓰면 프로젝트에서 금지하는 AI식 추상
상투구로 읽힐 수 있습니다.

예를 들어 다음과 같이 바꾸는 편이 낫습니다.

- `품질을 일관되게 유지할 수 있는 기반을 마련했습니다`
  → `Playwright E2E를 배포 필수 게이트로 편입했습니다`
- `팀이 같은 기준으로 판단할 수 있는 구조로 바꿨습니다`
  → `개발 표준을 사내 공식 문서로 채택하고 팀 10명의 개발 절차에 적용했습니다`
- `운영 변경에 빠르게 대응할 수 있는 기반을 마련했습니다`
  → `고객사별 CI·메뉴·기능 변경을 1주 안에 반영할 수 있게 했습니다`

### 3. 이력서의 나열을 자기소개서의 서사로 바꾸기

현재는 한 문단 안에 SSE, Config, Markdown, E2E, PostHog, GA4, Storybook,
Chromatic, Jenkins가 계속 등장합니다. 이력서에서 이미 확인할 수 있는 도구
목록보다 다음 질문에 답하는 문장이 필요합니다.

- 어떤 문제를 보고 본인이 먼저 판단했는가
- 여러 선택지 중 왜 그 방법을 택했는가
- 본인의 결정으로 사용자나 팀의 행동이 무엇이 달라졌는가
- 이 경험이 지원 직무에서 어떤 방식으로 재현될 수 있는가

### 4. 검증된 수치도 원래 측정 범위로 쓰기

프로젝트의 개인 선호 규칙은 정량 성과를 `이전값 → 이후값`으로 쓰고,
퍼센트는 괄호 안 보조값으로만 두도록 정하고 있습니다.

- `LLM 응답 체감 속도 60% 단축`
  → `AI 답변 출력 시간을 10초 → 4초(약 60%)로 단축`
- `페이지 접근 속도 개선`
  → `페이지 접근 시간을 8초 → 2초로 단축`
- `반복 컴포넌트 개발 시간 단축`
  → `반복 컴포넌트 개발 시간을 90분 → 15분(약 83%)으로 단축`

`체감 속도`는 측정 대상이 모호하므로 쓰지 않는 편이 안전합니다.

## 초안별 평가

### 1. 서비스와 조직을 함께 설계하는 프로덕트 엔지니어

**평가: 전체 자기소개서의 뼈대로 가장 적합합니다.**

좋은 점:

- `base-resume.pdf`의 Product Engineer 포지셔닝과 가장 잘 맞습니다.
- AI 챗봇 제품화, 플랫폼 내재화, 품질 체계, 조직 자산화가 자연스럽게
  연결됩니다.
- 제품과 팀을 함께 개선한다는 주제가 경력 전체를 포괄합니다.

보완할 점:

- 한 글 안에 핵심 주제가 네 개라서 어느 것도 깊게 남지 않습니다.
- 첫 두 문단만으로도 충분한데 문서화, 품질, 세미나가 각각 별도 문단으로
  이어져 이력서 요약처럼 보입니다.
- `프론트엔드 단독 담당에 가까운 역할`은 모호합니다. 근거상 AI 챗봇의
  프론트엔드 총괄·설계·구현·테스트를 맡았으므로 책임 범위를 정확히
  표현하는 편이 낫습니다.
- `AI코치와 비즈케어`는 최종 문서에서 제품명을 통일해야 합니다.
  `비즈36.5`와 `AI코치` 또는 프로젝트 성격을 설명하는 일반명 중 하나를
  선택해야 합니다.

권장 편집:

- AI 챗봇 제품화 문단을 대표 사례로 유지합니다.
- 문서화·품질·세미나 세 문단은 “팀 AX 전환” 한 문단으로 합칩니다.
- 전체 분량을 현재의 약 55~65%로 줄입니다.

### 2. 적극적인 문제해결사, 팀의 흐름을 바꾸는 개발자

**평가: 주제는 명확하지만 현재 상태로는 사실 안전성이 가장 낮습니다.**

좋은 점:

- 문제를 기다리지 않고 병목을 제거한다는 행동 원칙이 선명합니다.
- 성능 최적화와 AI 서비스 운영을 같은 문제 해결 방식으로 연결한 점은
  좋습니다.

보완할 점:

- `백엔드 API 준비 지연 → Node.js·Express 더미 서버 구축` 사례는 현재
  `experience-bank.md`에서 확인되지 않습니다. 근거 은행에 있는 것은
  React 프론트 전용 BFF API를 팀 공동으로 신규 구축한 경험입니다.
  두 경험을 섞으면 안 됩니다.
- 더미 서버 사례를 실제로 사용하려면 프로젝트, 시기, 본인 역할, 결과를
  먼저 확인해 근거 은행에 추가해야 합니다.
- Next.js의 SSR/CSR 판단은 한국 웹 구현 범위의 판단입니다. 전체
  아키텍처는 일본 본사 설계였다는 귀속 범위를 유지해야 합니다.
- 세 번째와 네 번째 문단이 다른 초안과 거의 중복됩니다.

권장 편집:

- 현재의 더미 서버 문단은 제거합니다.
- 대신 근거가 명확한 `API 응답 시점과 화면 노출 시점을 분리 측정해 병목을
  특정하고, React Native 검색 결과 노출을 5초 → 1초로 단축한 사례`를
  쓰면 문제 해결 문항에 더 강합니다.

### 3. 사용자 경험을 성능과 안정성으로 증명하는 프론트엔드 개발자

**평가: 사용자 경험 또는 성능 문항용으로 좋습니다.**

좋은 점:

- “보기 좋은 화면”이 아니라 속도·안정성·에러 대응으로 UX를 정의한 첫
  문단이 명확합니다.
- 페이지 접근 8초 → 2초는 확인된 수치여서 설득력이 있습니다.
- Lighthouse, GA, Adobe Analytics, Datadog 활용은 근거와 일치합니다.

보완할 점:

- `공통 ErrorHandler 유틸`, HTTP 코드별 매핑 사례는 현재 근거 은행에서
  확인되지 않습니다. 확인 전에는 외부 제출본에서 빼는 편이 안전합니다.
- SSR/CSR을 본인이 전체 아키텍처 차원에서 설계한 것처럼 읽히지 않도록
  `일본 본사 아키텍처 위에서 한국 웹의 페이지별 렌더링 경계를 판단했다`고
  범위를 밝혀야 합니다.
- `Session Replay`는 현재 표준 근거 파일에서 확인되지 않습니다.
- 기술 설명이 길어 사용자에게 무엇이 달라졌는지가 뒤로 밀립니다.

권장 편집:

- 첫 문단 → 8초에서 2초 사례 → 운영 데이터로 개선한 방식 → 지원 직무
  기여의 4문단으로 압축합니다.
- ErrorHandler와 Session Replay는 근거 확인 후 사용합니다.

### 4. 데이터와 대안으로 협업을 조율하는 개발자

**평가: 협업 문항의 방향은 좋지만 대표 사례를 교체해야 합니다.**

좋은 점:

- 커뮤니케이션을 말솜씨가 아니라 공통 판단 기준을 만드는 능력으로 정의한
  점이 좋습니다.
- 데이터, 시각화, 실행 가능한 대안이라는 세 가지 수단이 명확합니다.

보완할 점:

- `장바구니 전체 로딩 요구 → Lighthouse LCP 근거로 페이지네이션 제안`
  사례는 현재 근거 은행에서 확인되지 않습니다.
- 근거 은행에는 삼성물산 사례의 서버 페이지네이션이 “향후 개선 방향이며
  미적용”이라고 명시되어 있습니다. 서로 다른 프로젝트라고 하더라도 현재
  문장만으로는 실제 적용 사례인지 검증할 수 없습니다.
- `Figma 기반 디자인 시스템 정리`와 Storybook 협업의 세부 범위도 현재
  확정 근거보다 넓게 서술되어 있습니다.
- 네 개 사례가 모두 짧게 등장해 협업 과정의 갈등과 조율 결과가 충분히
  드러나지 않습니다.

권장 편집:

- 확인되지 않은 장바구니 사례 대신 `Storybook 스토리 210개를 활용해
  기획자와 UI를 조기 확정하고 기획–개발 검증 리드타임을 2일 → 1일로
  줄인 사례`를 중심에 둡니다.
- 한 사례에서 `관점 차이 → 제시한 근거 → 선택한 대안 → 바뀐 결과`를
  끝까지 보여주는 편이 좋습니다.

### 5. AI 시대의 개발 생산성을 구조화하는 프론트엔드 엔지니어

**평가: 차별성이 가장 강하며, 첫 번째 글에 결합할 핵심 소재입니다.**

좋은 점:

- AI 도구 사용 경험이 아니라 AI 생성 코드를 어떻게 신뢰할 것인지까지
  다뤄 차별성이 큽니다.
- Playwright, Storybook, CI/CD를 검증 기준으로 연결한 경험은
  `base-resume.pdf`의 팀 AX 전환 사례와 잘 맞습니다.
- 반복 컴포넌트 개발 90분 → 15분은 확인된 수치입니다.

보완할 점:

- `Figma MCP`, `Storybook MCP`, `SKILL.md`, `AGENT.md`는 현재 근거
  은행에서 확인되지 않습니다. `AGENT.md`는 일반적인 파일명
  `AGENTS.md`와도 다르므로 오기 가능성이 있습니다.
- `신규 차트 개발 1시간 → 10분`은 수치 레지스트리와 경험 은행에서
  확인되지 않습니다. 확인 전에는 삭제해야 합니다.
- 현재 문장은 도구 이름이 많아 “왜 이 체계가 필요했는가”보다 도구 사용
  자랑처럼 읽힐 수 있습니다.
- 제목이 `프론트엔드 엔지니어`로 끝나 첫 번째 글의 Product Engineer
  포지셔닝과 충돌합니다.

권장 편집:

- 검증 가능한 표현인 `Claude Code·Codex 기반 하네스 엔지니어링`,
  `Playwright E2E 배포 필수 게이트`, `Storybook 스토리 210개`,
  `개발 표준의 사내 공식 문서 채택`, `팀 10명의 개발 절차로 정착`을
  중심으로 재작성합니다.
- 도구명보다 “AI 생성 코드의 신뢰 기준을 정의했다”는 판단을 첫 문장에
  둡니다.

## 권장 최종 구조

대상 회사의 자유 형식 자기소개서가 1,000~1,500자라고 가정하면 다음
구조가 적합합니다.

1. **정체성**  
   프론트엔드에서 풀스택·AI까지 확장한 Product Engineer이며, 제품과
   개발 방식을 함께 개선해 왔다는 한 문장
2. **대표 제품 사례**  
   AI 챗봇 10주 제품화, SSE·Markdown·Config-Driven 설계, 400건 검증
   정상 출력률 100%, 신규 고객사 FE 커스터마이징 2주
3. **차별화 사례**  
   AI 생성 코드의 신뢰 문제를 발견하고 Playwright E2E 필수 게이트,
   Storybook 210개, 개발 표준 공식 문서 채택으로 팀 10명의 절차를 바꾼 경험
4. **지원 직무 기여**  
   지원 회사의 제품·조직 문제와 위 두 경험이 어떻게 연결되는지 구체적으로
   제시

제목은 다음 정도가 가장 일관됩니다.

> 제품과 개발 방식을 함께 개선하는 Product Engineer

현재 첫 제목의 장점을 살리면서도 “조직을 설계한다”는 다소 큰 표현을
줄일 수 있습니다.

## 다음 수정 시 필요한 정보

제출 가능한 최종본으로 만들려면 다음 세 가지가 필요합니다.

- 대상 회사와 JD

없습니다. 현재 원고는 위 기준으로 먼저 정리한 뒤, 회사별로 사례 순서와
마지막 문단만 바꾸는 방식이 효율적입니다.
