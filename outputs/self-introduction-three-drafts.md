# 자기소개서 3종 초안

## 1. 설계부터 운영까지 책임지는 Product Engineer

프로젝트를 시작하면 바로 개발 일정부터 잡지 않습니다. 먼저 전략·기획 담당자와 서비스의 목적, 사용자가 해야 할 일, 운영 시 달라질 조건을 확인합니다. 요청이 모호하면 화면과 기능 단위로 나누고, 구현 가능한 문제로 다시 정의합니다. 그다음 완성된 사용 흐름을 목업으로 먼저 구체화해 관계자와 합의합니다. 이 과정에서 구현 난도가 높은 부분과 선행 결정이 필요한 부분을 일찍 드러내야, 개발 중간에 방향을 되돌리는 일을 줄일 수 있습니다.

대웅제약 AI추진팀에서 목업 수준의 AI 건강검진 챗봇을 10주 안에 실서비스로 전환할 때도 같은 순서로 일했습니다. 기획자와 MVP 범위를 정하고, AI 개발자와는 응답 형식·스트리밍 방식·오류 정책을 개발 전에 합의했습니다. 사용자가 질문하고 답변을 기다리는 과정부터 중지·재시도와 오류 안내까지 목업으로 확인하면서, 기획 의도와 실제 구현 사이의 차이를 먼저 좁혔습니다. 답변의 형식과 길이가 매번 달라질 수 있다는 점처럼 뒤늦게 발견하면 일정에 영향을 주는 문제도 이 단계에서 함께 검토했습니다.

합의한 내용은 WBS로 나눠 작업 순서와 ETA를 정했습니다. 화면 개발, AI·백엔드 연동, 예외 처리, 검증 항목 사이의 의존 관계를 표시하고, 다른 직군의 결정이 필요한 항목은 먼저 확인했습니다. 구현 중 예상과 다른 결과가 나오면 해당 담당자에게 문제와 선택지를 함께 전달했습니다. 단순히 어렵다고 보고하기보다 일정·사용성·운영 부담에 미치는 영향을 비교해, 어느 대안을 택할지 빠르게 결정할 수 있도록 했습니다. 프론트엔드 설계부터 구현과 테스트까지 맡았지만, 혼자 판단해서 진행하지 않고 결정이 필요한 시점마다 관련 직군과 기준을 맞췄습니다.

테스트 단계에서는 정상 동작만 확인하지 않았습니다. 실제 사용 순서에 맞춰 응답 지연과 실패, 재시도 같은 상황을 점검하고 배포 전 판정 기준을 정했습니다. 운영 이후 고객사마다 문구와 기능 노출 조건이 달라질 가능성도 처음부터 반영했습니다. 그 결과 계획보다 2주 앞서 실서비스로 전환했습니다. 요구사항을 명확히 하고, 완성 모습을 먼저 합의하고, 위험한 지점을 앞당겨 해결하는 방식이 제가 제품을 빠르게 완성하는 방법입니다.

분량: 1,076자

## 2. 문제의 원인을 찾고 해결까지 책임지는 개발자

기존 소프트웨어를 맡으면 먼저 화면 뒤의 실행 경로를 따라갑니다. 요청이 어느 코드에서 시작되고, 어떤 데이터와 의존성을 거쳐 결과로 나오는지 확인합니다. 보이는 증상만 고치면 같은 원인이 다른 화면에서 다시 나타나기 쉽기 때문입니다. 평소에도 책임이 섞인 코드를 나누고 다음 수정이 쉬운 형태로 고치는 습관이 있습니다.

대웅제약의 임직원 건강 플랫폼을 내재화할 때 이 습관이 특히 중요했습니다. 2019년에 작성된 서비스는 Spring Boot 서버, Thymeleaf·jQuery 화면, MySQL 쿼리가 기능별로 강하게 얽혀 있었습니다. 외주 의존도가 높아 한 화면의 변경 범위도 파악하기 어려웠습니다. 저는 화면 요청이 서버 로직과 DB 조회를 거쳐 최종 결과로 나오는 과정까지 따라가며 코드·데이터·화면의 관계를 정리했습니다. 데이터가 만들어지고 변환되는 전 구간을 살펴, 수정할 책임이 서버 로직인지 쿼리인지 화면인지 좁혔습니다.

모든 코드를 새로 쓰는 방법도 검토했지만, 운영 중인 서비스를 한 번에 교체하면 일정과 장애 위험이 커집니다. 반대로 기존 방식을 그대로 두면 결합도가 높은 코드가 계속 쌓이게 됩니다. 그래서 jQuery·Thymeleaf 화면과 React가 화면 단위로 공존하는 island-loader 방식을 선택했습니다. 변경이 잦거나 장애 영향이 큰 화면부터 교체하고, 공통으로 반복되는 UI는 React 컴포넌트로 분리했습니다. 기존 서비스를 운영하면서도 새 화면의 책임을 분명히 나눌 수 있는 선택이었습니다.

이후 MySQL 데이터 모델부터 Spring Boot 서버 로직, REST API, Web·Admin 화면까지 직접 연결해 개발했습니다. 108개 페이지와 82개 화면을 9주 안에 단독으로 전환하면서도 새 화면으로 덮어쓰는 데 그치지 않았습니다. 새 기능이나 오류가 생겼을 때 시작점과 변경 범위를 추적할 수 있도록 화면, API, 데이터 처리의 책임을 나눴습니다. 리팩토링의 목적은 코드를 짧게 만드는 것이 아닙니다. 처음 작성한 사람이 없어도 동료가 실행 경로를 따라가며 원인을 찾고, 필요한 부분만 안심하고 수정할 수 있는 소프트웨어를 만드는 것입니다.

분량: 1,062자

## 3. AI 활용을 팀의 개발 방식으로 확장한 개발자

ChatGPT 유료 서비스가 시작된 초기부터 직접 결제해 업무와 학습에 사용했습니다. 처음에는 궁금한 내용을 묻고 코드 예시를 얻는 일이 많았습니다. GPT-4o를 사용하기 시작하면서 활용 방식이 달라졌습니다. 생성된 코드를 그대로 받아들이기보다 제가 작성한 코드의 선택 이유를 설명하고, 다른 접근법과 놓친 위험을 검토하게 했습니다. 문제의 조건과 제 판단을 다시 알려주며 결과를 다듬었고, AI를 정답을 주는 도구가 아니라 여러 관점에서 소스코드를 함께 검토하는 개발 파트너로 사용하게 됐습니다.

도구를 쓰는 데서 멈추면 결과를 판단할 수 없다고 보았습니다. 빅데이터분석기사를 공부하며 데이터 처리와 통계의 기초를 익혔고, 머신러닝 학습과 LLM 모델 구현 실습을 이어갔습니다. LangChain과 Hugging Face를 사용해 보고, RAG와 VectorDB가 답변에 필요한 정보를 어떻게 찾고 전달하는지도 직접 학습했습니다. 프로덕션용 LLM을 단독으로 개발한 경험은 아니지만, 작동 원리를 공부한 덕분에 어떤 일은 AI에 맡기고 어떤 결과는 개발자가 확인해야 하는지 구분할 수 있었습니다.

활용 방식은 프롬프트 엔지니어링에서 컨텍스트 엔지니어링으로, 다시 하네스 엔지니어링으로 발전했습니다. 질문을 잘 쓰는 것만으로는 프로젝트마다 다른 코드 규칙과 업무 맥락을 전달하기 어려웠습니다. 그래서 AI가 참고할 정보, 금지할 패턴, 사람이 검토할 항목을 정리했고, 생성된 코드가 타입 검사·테스트·빌드·E2E 검증을 통과해야 배포할 수 있도록 했습니다. AI의 결과를 믿는 대신 통과 조건을 코드와 개발 절차에 넣은 것입니다.

이 방법은 개인의 사용법에 머물지 않았습니다. 대웅제약 AI추진팀에서 프론트엔드 개발 기준으로 정리해 팀원 10명이 함께 사용하도록 했습니다. 반복 컴포넌트 개발 시간은 90분에서 15분으로, 반복 QA는 3시간에서 30분으로 줄었습니다. 검증에 쓰던 시간을 줄여 기능 개발과 코드 검토에 다시 사용할 수 있었습니다. 새로운 AI 도구를 접할 때마다 먼저 원리를 공부하고, 실무에서 효과와 한계를 확인한 뒤, 동료가 같은 결과를 재현할 수 있는 기준으로 만드는 것이 저의 활용 방식입니다.

분량: 1,072자

## 자체 점검

- 1번은 관계자 합의부터 운영까지 이어지는 제품화 방식, 2번은 레거시 실행 경로 분석과 점진적 리팩토링, 3번은 초기 AI 관심부터 원리 학습·활용 방식의 변화·팀 적용까지를 중심으로 분리했습니다.
- 동일한 AI 챗봇 경험을 1번과 3번에서 반복 서술하지 않았으며, 3번은 개발 방법과 검증 기준에만 초점을 맞췄습니다.
- 수치는 `metric-registry.md`와 사용자 확인 기록의 스코프를 따랐고, 확인되지 않은 더미 서버·문서명·MCP·차트 개발 시간은 제외했습니다.
- 한국미스미 SSR·CSR 사례는 소재 중복을 줄이기 위해 이번 세 초안에서 사용하지 않았습니다.
