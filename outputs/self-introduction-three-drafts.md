# 자기소개서 3종 초안

## 1. 설계부터 운영까지 책임지는 Product Engineer

대웅제약 AI추진팀에서 AI 건강검진 챗봇을 맡았을 때, 주어진 과제는 목업에 가까운 화면을 실제 고객이 사용할 수 있는 서비스로 바꾸는 일이었습니다. 프론트엔드 화면만 완성해서는 해결되지 않았습니다. LLM 답변이 늦거나 중간에 끊길 때의 처리, Markdown과 표가 섞인 답변의 출력, 고객사마다 달라지는 색상과 문구까지 운영 단계에서 생길 문제를 함께 풀어야 했습니다.

React와 TypeScript로 프론트엔드 아키텍처를 설계하고, 백엔드·LLM 개발자와 응답 정책을 조율했습니다. SSE 스트리밍을 적용해 답변이 생성되는 과정을 바로 보여주고, 중지·재시도·오류 상태를 대화 화면에 반영했습니다. Markdown 전용 렌더러와 XSS 필터링을 적용했으며, 네트워크·입력·인증·치명적 화면 오류를 나눠 사용자가 다음 행동을 선택할 수 있게 했습니다. 그 결과 AI 답변 출력 완료 시간을 10초에서 4초로 단축했고, 400건 발화 검증에서 답변 화면 정상 출력률 100%를 확인했습니다.

고객사가 늘어날 때마다 코드를 다시 만드는 방식도 바꿨습니다. Base-Theme과 Config-Driven UI로 색상·CI·문구·기능 노출 조건을 분리했습니다. 최초 챗봇 구현에 10주가 걸렸지만, 이후 신규 고객사의 프론트엔드 커스터마이징과 납품은 2주 만에 마쳤습니다. 이어 외주 중심이던 임직원 건강 플랫폼을 내재화하며 MySQL 데이터 모델, Spring Boot 서버 로직, REST API, Web·Admin 화면까지 직접 개발했습니다. 레거시 화면은 한 번에 걷어내지 않고 jQuery·Thymeleaf와 React가 공존하도록 나눠 전환했습니다.

이 경험을 통해 제 역할은 프론트엔드의 경계에서 끝나지 않는다는 점을 확인했습니다. 요구사항을 화면으로 옮기는 데 그치지 않고, 오류 정책과 데이터 처리, 고객사 확장, 배포 이후의 유지보수까지 살펴야 제품이 완성됩니다. 앞으로도 설계 단계의 판단을 운영 결과로 확인하며, 맡은 서비스를 끝까지 책임지는 Product Engineer로 일하겠습니다.

분량: 1,011자

## 2. 문제의 원인을 찾고 해결까지 책임지는 개발자

성능 문제를 해결할 때 가장 먼저 하는 일은 느린 구간을 나눠 확인하는 것입니다. 삼성물산 React Native 앱의 장비·인력 검색 화면은 수만 건의 데이터를 다뤘고, 검색 결과가 나타나기까지 약 5초가 걸렸습니다. 처음에는 API가 원인으로 보였지만 추측만으로 서버를 수정하지 않았습니다. API 응답이 끝나는 시점과 화면에 목록이 나타나는 시점을 따로 측정했고, 병목이 클라이언트 렌더링에 있다는 사실을 확인했습니다.

FlatList 가상화를 적용하고 안정적인 key를 사용했으며, renderItem과 항목 컴포넌트의 불필요한 재렌더링을 줄였습니다. getItemLayout으로 항목 크기를 반복 측정하는 비용도 없앴습니다. 검색 입력에는 debounce를 적용하고, 같은 조건의 조회에는 React Query 캐시를 사용했습니다. 이전 요청을 취소해 늦게 도착한 응답이 최신 검색 결과를 덮어쓰지 않도록 처리했습니다. 이러한 개선으로 검색 응답 시간을 5초에서 1초로 단축했습니다.

웹 대시보드에서도 같은 원칙을 적용했습니다. 데이터를 한 번에 불러와 테이블과 차트를 동시에 그리면서 화면이 멈추는 현상이 있었습니다. 우선 노출해야 할 데이터와 나중에 불러와도 되는 데이터를 구분하고, 렌더링 순서를 분리했습니다. 프론트엔드만 손보지 않고 Spring REST API의 응답도 함께 살폈습니다. 필요한 컬럼만 담는 DTO로 응답을 가볍게 만들고, 조회 조건에 맞춰 DB 인덱스를 조정해 대시보드 렌더링 시간을 2.5초에서 1초대로 줄였습니다.

모든 문제에 같은 해법을 적용하지는 않습니다. 데이터가 적으면 클라이언트 필터링이 빠르지만, 수만 건이 계속 늘어나는 상황이라면 서버 검색과 페이지네이션이 더 안정적입니다. 전역 상태 역시 편하다는 이유만으로 늘리지 않고, 서버 상태는 React Query, 화면 안에서만 쓰는 값은 로컬 상태, 여러 화면이 공유하는 값만 전역 상태로 구분했습니다. 저는 기술을 먼저 고르기보다 병목을 측정하고, 데이터 규모와 변경 비용을 기준으로 해법을 선택합니다. 그리고 선택한 해법이 실제 수치로 개선됐는지까지 확인합니다.

분량: 1,041자

## 3. AI 활용을 팀의 개발 방식으로 확장한 개발자

AI 코딩 에이전트를 실무에 도입하면서 가장 먼저 부딪힌 문제는 코드 생성 속도가 아니었습니다. 같은 요청에도 결과가 달라졌고, 프로젝트의 규칙을 모르면 빠르게 만든 코드가 오히려 검토 시간을 늘렸습니다. 개인이 프롬프트를 잘 쓰는 것만으로는 팀의 개발 방식이 바뀌지 않는다고 판단했습니다. 그래서 대웅제약 AI추진팀의 프론트엔드 영역에서 AI가 참고할 맥락과 사람이 확인할 기준을 함께 정리했습니다.

먼저 컴포넌트 작성 규칙, 상태 관리 범위, 예외 처리 방식, 금지 패턴과 보안 주의사항을 FE AX SOP로 문서화했습니다. Codex와 Claude Code가 코드를 만들더라도 TypeScript 타입 검사, 테스트, 빌드 결과를 거쳐야 다음 단계로 넘어가도록 했습니다. Storybook에서는 컴포넌트의 상태와 변형을 확인하고, Playwright에서는 로그인부터 주요 화면 이용까지 실제 사용자 동선을 검증했습니다. 도구를 많이 붙이는 것이 목적이 아니라, 누가 작업하더라도 같은 항목을 확인하도록 판정 기준을 맞추는 데 집중했습니다.

반복되는 검증은 자동화했습니다. Playwright E2E 시나리오 5종을 직접 설계해 배포 과정의 필수 검사로 적용했고, 반복 QA 시간을 3시간에서 30분으로 단축했습니다. 컴포넌트의 반복 구현 방식도 정리해 개발 시간을 90분에서 15분으로 줄였습니다. 이 기준은 프론트엔드 관련 업무를 수행하는 팀원 10명 전원이 사용하고 있으며, 담당자가 자리를 비워도 동일한 절차로 검증하고 배포할 수 있게 됐습니다.

새로운 방법을 문서로만 남기지 않았습니다. 외부 컨퍼런스와 실무에서 확인한 내용을 사내 개발 세미나 12회에 걸쳐 공유했고, 실제 프로젝트에서 불편했던 부분을 다시 규칙에 반영했습니다. 이 과정에서 AI는 개발자를 대신하는 도구가 아니라, 팀이 이미 합의한 기준을 더 빠르게 실행하는 수단이라는 결론을 얻었습니다. 앞으로도 새로운 도구를 먼저 자랑하기보다, 팀이 안심하고 사용할 수 있는 조건을 정리하고 실제 개발 시간과 품질의 변화로 효과를 확인하겠습니다.

분량: 1,013자

- 동일한 AI 챗봇 경험을 1번과 3번에서 반복 서술하지 않았으며, 3번은 개발 방법과 검증 기준에만 초점을 맞췄습니다.

- 한국미스미 SSR·CSR 사례는 소재 중복을 줄이기 위해 이번 세 초안에서 사용하지 않았습니다.
