## 1. 화면에서 시작해 제품 전체로 책임 범위를 넓혔습니다

저는 프론트엔드 개발자로 커리어를 시작해 풀스택과 AI 영역까지 확장해 온
6년차 Product Engineer입니다. 새로운 기술을 많이 다루는 것보다, 사용자가
겪는 문제의 원인이 있는 곳까지 들어가 해결하는 방식으로 역할을 넓혀
왔습니다.

내담씨앤씨 소속으로 참여한 한국미스미 프로젝트에서는 PHP·jQuery 기반
글로벌 B2B 커머스를 Next.js·React·TypeScript로 전환했습니다. 화면을
교체하는 데 그치지 않고 렌더링 방식과 리소스 병목을 분석해 페이지 접근
시간을 8초에서 2초로 줄였습니다. 이후 삼성물산 프로젝트에서는 Vue 3
대시보드와 React Native 앱의 프론트엔드 병목뿐 아니라 Spring·Oracle의
인덱싱과 응답 모델까지 직접 조정했습니다. 문제를 해결하려면 화면과 서버를
나누어 볼 수 없다는 사실을 이 과정에서 배웠습니다.

현재는 대웅제약 AI추진팀에서 React·Next.js 프론트엔드부터
Node.js·Spring Boot·MySQL, LLM 응답 처리와 배포 검증까지 신규 기능의 전
과정을 맡고 있습니다. 프론트엔드에서 쌓은 사용자 관점을 출발점으로 삼되,
필요한 계층을 넘나들며 제품의 완성도와 운영 가능성까지 책임지는 것이 제가
일하는 방식입니다.

## 2. 불확실한 AI를 3,493명이 사용하는 서비스로 전환했습니다

AI 건강검진 챗봇을 10주 안에 실서비스로 전환하는 프로젝트를 맡았습니다.
PoC 단계의 LLM은 응답 형식과 품질이 매번 달랐고, 프론트엔드가 어떤 결과를
보장해야 하는지도 정해지지 않은 상태였습니다. 저는 구현부터 시작하지 않고
기획자와 MVP 범위를 정한 뒤 AI 개발자와 응답 형식·스트리밍 방식·오류
정책을 먼저 합의했습니다.

합의한 기준을 바탕으로 SSE 실시간 응답과 중지·재시도·재생성·상담 이력을
구현했습니다. Markdown 응답은 표·차트·링크를 표시하는 React 컴포넌트로
변환하고, XSS·HTTP 오류·LLM 오류를 유형별로 나누어 사용자가 다시 시도할
수 있는 방법을 제공했습니다. 고객사별 과금과 기능 차등 요구에는
Base-Theme·Config-Driven UI를 적용해 운영·기획 담당자가 테마와 기능
노출을 직접 조정하도록 만들었습니다.

그 결과 계획보다 2주 빠르게 임직원 3,493명 규모의 실사용 서비스로
전환했습니다. 실사용 발화 400여 건 검증을 통과했고, Vitest 약 2,600개와
Playwright E2E를 적용해 반복 QA 시간을 3시간에서 30분으로 줄였습니다.
최초 구현에 10주가 필요했던 프론트엔드 범위는 신규 고객사
커스터마이징에서 2주 만에 납품할 수 있었습니다. 이 경험을 통해 불확실한
기술을 제품으로 만드는 핵심은 기능 수가 아니라, 무엇을 보장하고 실패했을
때 어떻게 복구할지를 먼저 정하는 데 있다는 것을 확인했습니다.

## 3. AI 활용보다 검증 기준과 팀 정착을 먼저 만들었습니다

AI 도구를 개발에 도입하면서 가장 먼저 본 문제는 코드 생성 속도가
아니었습니다. 사람마다 다른 지시와 검증 방법을 사용하면 결과의 편차가
커지고, 담당자가 바뀔 때 같은 품질을 재현하기 어려웠습니다. 저는 도구
사용법을 공유하는 대신 AI가 만든 코드를 팀이 어떤 기준으로 검증하고
배포할지를 먼저 정했습니다.

컨텍스트 관리·금지 패턴·보안 위험·필수 검증 절차를 FE AX 개발 표준으로
설계하고, 발화 테스트·LLM 응답 검증·타입 검사·빌드·배포 전후 확인을
자동으로 실행하는 하네스를 만들었습니다. Playwright E2E는 배포의 필수
게이트로 편입했습니다. Storybook 스토리 210개로 공통 컴포넌트를
카탈로그화하고, 개발 세미나 12회와 기술 문서 48건으로 판단 기준과
사용법을 남겼습니다.

이 표준은 10명 스쿼드 전원의 개발 방식으로 정착했습니다. 반복 컴포넌트
개발 시간은 90분에서 15분으로 줄었고, Storybook으로 UI를 먼저 확인하면서
기획·개발 검증 리드타임도 2일에서 1일로 단축됐습니다. 담당자가 없어도
같은 기준으로 검증과 배포를 이어갈 수 있게 되었습니다. 저는 새로운 도구를
빠르게 사용하는 데서 멈추지 않고, 동료가 반복해서 활용할 수 있는 기준과
문서로 남길 때 조직의 역량이 된다고 생각합니다.
