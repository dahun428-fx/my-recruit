# 자기소개서 v2 — 현대오토에버(주) 계정 시스템 프론트엔드 개발 및 운영 (신규 작문 v1 · 2026-10-29)

## 항목 1 · 빠른지, 숫자로 증명되는지, 안전한지를 함께 판단합니다

저는 프론트엔드의 품질을 기능이 동작하는지가 아니라 **화면이 얼마나 빨리 뜨는지, 그 개선을 숫자로 증명할 수 있는지, 사용자 데이터를 안전하게 다루는지의 세 기준으로 판단합니다.** 프로젝트가 바뀌어도 이 기준은 바꾸지 않았습니다.

렌더링 성능은 페이지마다 비용이 다르다는 전제에서 출발합니다. 한국미스미 커머스의 Next.js 전환에서는 상품·검색 유입 페이지는 SEO와 초기 로드를 위해 SSR로, 로그인 후 상호작용 중심 페이지는 CSR로 나누고 code splitting·next/image·prefetch·Lazy Loading을 적용해 **기존 PHP 서비스 대비 평균 로딩 속도를 약 50% 개선했습니다(GA 기준).** 삼성물산 현장 앱에서는 수만 건 목록을 FlatList 가상화와 재렌더링 제거로 바꿔 **검색 결과 노출을 5초에서 1초로 줄였고,** 대웅제약에서는 React Query staleTime으로 같은 데이터의 재요청을 줄여 동일 엔드포인트 연쇄 호출을 8개에서 5개로, HTTP/2·캐시 최적화로 LCP를 2.6초에서 1.5초로 낮췄습니다.

개선은 추정이 아니라 측정에서 시작합니다. 삼성물산 앱의 검색이 느렸을 때 "API가 느릴 것"이라고 단정하지 않고 API 응답 시점과 화면 노출 시점을 나눠 측정해 **병목이 클라이언트 렌더링에 있다는 것을 먼저 확인했습니다.** 개선 효과도 같은 기준으로 다시 잽니다. 웹 성능은 Lighthouse와 Web Vitals의 LCP로, 서비스 지표는 GA·Adobe Analytics·Datadog·PostHog로 지표화했고, 반복 검증은 주요 사용자 흐름 24개 시나리오·248개 Step·3개 Viewport로 범위를 고정해 자동화한 뒤 **해당 범위의 검증 시간을 30분에서 5분으로 줄였습니다.**

보안은 화면에 무엇을 그리고 토큰을 어디에 두는지에서 결정된다고 봅니다. AI 건강검진 챗봇에서는 LLM이 만든 Markdown을 그대로 그리지 않고 **정규화 → XSS 필터링 → 토큰화 → 노드 매핑을 거쳐 React 컴포넌트로 렌더링하는 계층을 직접 설계했습니다.** 두 SI 프로젝트(삼성물산·한국미스미)에 걸친 SSO·OAuth 2.0 연동에서는 **콜백의 state를 검증해 CSRF를 막고, Access 토큰은 메모리에, Refresh 토큰은 서버가 설정하는 httpOnly 쿠키에 두도록 연동해 XSS 노출을 줄였습니다.** AI 생성 코드가 늘어난 뒤에는 금지 패턴과 비밀키 노출을 코드 편집 단계에서 자동 점검하고, 이 기준을 FE AX 개발 표준에 담아 팀이 같은 기준으로 쓰게 했습니다.

**빠르게 보이는 화면이 아니라, 빠르다는 것을 숫자로 보여 줄 수 있고 사용자의 데이터를 안전하게 다루는 화면을 만드는 것이 제가 생각하는 프론트엔드 엔지니어의 일입니다.**

## 항목 2 · 맡겨진 레거시에서 출발해, 다음 기술로 가는 길을 스스로 냈습니다

SI 회사에서 처음 투입된 곳은 PHP·jQuery로 운영되던 한국미스미 글로벌 B2B 커머스였습니다. 프로젝트 배정은 회사가 정하지만, 어떤 기술로 일할 수 있는 개발자가 될지는 제가 정할 수 있다고 생각했습니다. 그래서 Vue·React 같은 SPA 기술을 꾸준히 학습하고 그 역량을 어필했고, **일본 본사 주도의 Next.js 전면 전환에 투입되어 한국 팀 6인의 마이그레이션을 이끌었습니다.** 이후에는 Vue 3 대시보드와 React Native 앱을 함께 개발하는 삼성물산 프로젝트로 이어졌습니다.

SI에서는 라이브러리와 스택을 고를 권한이 없었습니다. 대신 주어진 스택 안에서 구현 수준의 판단은 스스로 내렸습니다. 삼성물산 앱에서는 서버 상태는 React Query, 화면 상태는 로컬, 여러 화면이 공유하는 값만 Recoil 전역으로 두었고, **데이터 규모를 기준으로 클라이언트 필터링과 서버 검색의 경계를 직접 정했습니다.** 선택마다 반대로 갔을 때의 비용을 설명할 수 있어야 한다고 생각했기 때문입니다.

ChatGPT-4o가 나왔을 때는 AI 기술을 익혀야 한다고 느꼈습니다. LangChain·RAG 같은 LLM 기술을 스스로 공부한 뒤 AI 제품을 만드는 조직으로 옮기기로 했고, **대웅제약 AI추진팀에 합류해 AI 건강검진 챗봇의 프론트엔드를 총괄하며 임직원 3,493명이 쓰는 서비스로 출시했습니다.**

AI를 개인의 도구로 쓰는 데서 멈추지 않았습니다. AI가 만든 코드를 같은 기준으로 검증하는 하네스와 FE AX 개발 표준을 설계해 **10명 팀 전원의 개발 방식으로 정착시켰습니다.** 레거시에서 최신 SPA로, 다시 AI를 팀의 방식으로 바꾸기까지 **저는 주어진 자리에서 다음 단계를 스스로 준비해 온 개발자입니다.**

## 항목 3 · 더 많은 사용자가 처음 만나는 화면을, 더 큰 팀의 표준으로 만들고 싶습니다

지금까지 제가 다뤄 온 화면의 사용자는 임직원 3,493명이 쓰는 사내 서비스와 월 방문자 약 112만(GA·Adobe Analytics 기준)의 B2B 커머스였습니다. 그 안에서 성능을 숫자로 개선해 왔고, 이제는 **훨씬 큰 사용자 규모에서 같은 기준으로 성능과 안정성을 책임지고 싶습니다.**

플레오스 2.0의 계정·인증 화면은 현대자동차·기아·제네시스 고객이 서비스를 이용하기 전에 가장 먼저 거치는 입구라고 생각합니다. 로그인이 느리거나 토큰 만료 처리가 어긋나면 그 뒤의 서비스 경험 전체가 영향을 받습니다. 두 SI 프로젝트에 걸쳐 SSO·OAuth 2.0 연동의 프론트엔드를 맡아 콜백 처리와 토큰 갱신·보관 방식을 직접 다뤄 왔기에, **계정 시스템 프론트엔드는 제 경험이 가장 직접 닿으면서 더 큰 규모를 책임질 수 있는 자리라고 판단해 지원했습니다.**

또 하나는 디자인 시스템과 표준입니다. 대웅제약과 다나아데이터에서 3개 서비스의 프론트엔드를 총괄하며 **변경 이유가 같은 UI만 공통 컴포넌트로 올리고, 고객사별 차이는 Base-Theme·Config-Driven 설정과 로고·컬러 토큰으로 분리했습니다.** Storybook 스토리 210개로 컴포넌트를 카탈로그화해 기획–개발 검증 리드타임을 2일에서 1일로 줄였고, 개발 표준과 검증 하네스는 10명 팀 전원의 방식으로 정착시켰습니다.

다만 이것은 한 팀, 세 서비스 규모의 공통화였습니다. **FE엔지니어링팀이 디자인 시스템 구축과 기술 Governance·표준 Toolchain을 함께 다룬다는 점에서, 작은 규모로 검증해 온 공통화와 표준화를 더 큰 조직의 디자인 시스템으로 키워 보고 싶습니다.** 입사 후에는 계정·인증 화면의 구조와 운영 지표부터 익히고, 측정으로 병목을 찾는 방식과 공통 컴포넌트·표준을 정착시켜 본 경험으로 팀의 기준을 함께 만들어 가겠습니다.
