## 요구를 아키텍처로 번역해 제품을 완성합니다 — 프론트엔드에서 API·배포까지

프로젝트를 시작하면 개발 일정부터 잡지 않습니다. 기획자·AI 개발자·운영 담당자와 서비스의 목적과 사용자가 해야 할 일부터 확인합니다. 대웅제약 AI추진팀에서 목업 수준의 AI 건강검진 챗봇을 10주 안에 실서비스로 올려야 했을 때도 같은 순서로 일했습니다. 기획자와 MVP 범위를 정하고, AI 개발자와는 응답 형식·스트리밍 방식·오류 정책을 개발 전에 합의했습니다. LLM 출력은 형식과 품질이 매번 달라진다는 점을 뒤늦게 발견하면 일정 전체가 흔들리기 때문에, 화면에서 무엇을 보장할 수 있는지부터 정의하고 시작했습니다.

이렇게 전제를 확정한 뒤 SSE 기반 실시간 스트리밍과 중지·재시도·상담 이력 흐름을 구현했습니다. 개발 도중에는 기능별로 차등 과금하려는 회사의 요구가 들어왔습니다. 저는 이 요구를 아키텍처 문제로 번역해, 이미 완성돼 있던 코드베이스의 대규모 리팩토링을 감수하고 Base-Theme·Config-Driven UI 구조로 전환했습니다. 이 구조에서는 운영자와 기획자가 고객사별 테마·기능 노출을 코드 수정 없이 설정으로 직접 제어합니다. 그 결과 이 챗봇은 임직원 3,493명이 실사용하는 서비스가 됐고, 이후 신규 고객사가 들어올 때 색상·CI·기능을 커스터마이징한 프론트엔드를 2주 만에 납품할 수 있었습니다. 최초 구현에 10주가 걸렸던 것과 비교하면, 완성된 코드의 리팩토링을 감수하고 확장 구조로 갈아탄 판단이 제품을 빠르게 재사용하는 길을 열었습니다.

## 원인을 추적하고, 한 번에 갈아엎지 않습니다

기존 소프트웨어를 맡으면 화면 뒤의 실행 경로부터 따라갑니다. 요청이 어느 코드에서 시작되고 어떤 의존성을 거쳐 결과로 나오는지 확인해야, 증상만 고쳤다가 같은 원인이 다른 화면에서 다시 나타나는 일을 막을 수 있습니다. 이 방식은 성능 문제에서 특히 유효했습니다. 내담씨앤씨에서 삼성물산 현장 데이터 플랫폼에 파견됐을 때, 대시보드가 느린 원인을 "API가 느릴 것"이라 추정하는 대신 API 응답 시점과 화면 노출 시점을 분리해 측정했습니다. 그 결과 병목이 서버가 아니라 클라이언트 렌더링 구간에 있음을 특정하고, 렌더링 생명주기 분리로 대용량 대시보드 렌더링을 2.5초에서 1초대로 줄였습니다.

대웅제약의 2019년 임직원 건강검진 서비스는 더 큰 전환이 필요한 경우였습니다. Spring Boot 서버와 Thymeleaf·jQuery 화면, MySQL 쿼리가 강하게 얽혀 있고 외주 의존도가 높아 한 화면의 변경 범위조차 파악하기 어려웠습니다. 저는 화면 요청이 서버와 DB를 거쳐 결과로 나오는 전 구간을 먼저 정리했습니다.

전환 방식을 정할 때는 두 비용을 함께 계산했습니다. 모든 코드를 새로 쓰면 운영 중인 서비스의 일정과 회귀 장애 위험이 커지고, jQuery를 오래 남겨 두면 두 방식이 공존하며 유지비와 화면 제어권 충돌이 쌓입니다. 그래서 서비스를 멈추지 않도록 jQuery·Thymeleaf 화면 위에 React 컴포넌트를 화면 단위로 심어 재사용하고, 변경·장애가 잦은 화면부터 교체하는 점진 전환을 택했습니다. 이렇게 108개 페이지·82개 화면을 9주 안에 단독으로 전환했고, 화면의 UI 회귀는 Playwright 기반 E2E 검증으로 자동화해 사람 대신 반복 확인하도록 했습니다. 신규 건강관리 기능은 여기서 더 나아가 MySQL 데이터 모델부터 서버 로직, REST API, 화면까지 직접 연결해 개발했습니다. 전환의 목적은 코드를 짧게 만드는 것이 아니라, 처음 작성한 사람이 없어도 필요한 부분만 안심하고 고칠 수 있게 하는 데 있었습니다.

## AI 활용을 도구에서 원리로, 다시 검증 구조로 넓힙니다

실무에서 저는 AI 챗봇 서버의 프롬프트 구성과 응답 후처리 로직을 직접 개선했습니다. 특히 LLM이 내놓는 Markdown 응답을 표·링크로 변환하는 후처리를 다듬어 화면에서 안정적으로 렌더링되게 했습니다. VectorDB·RAG 구현에도 참여해 답변에 필요한 정보가 어떻게 검색되고 전달되는지 확인했습니다. 프로덕션용 LLM을 단독으로 개발한 수준은 아니지만, 작동 방식을 실무에서 다뤄 본 덕분에 어떤 일을 AI에 맡기고 어떤 결과를 개발자가 반드시 확인해야 하는지 구분할 수 있게 됐습니다. 그래서 생성된 코드를 그대로 받기보다 제 선택의 이유를 설명하고 놓친 위험을 되묻는 방식으로 씁니다. AI를 정답을 내주는 도구가 아니라 여러 관점에서 코드를 함께 따져 보는 상대로 대하는 것입니다.

활용 방식은 프롬프트 엔지니어링에서 컨텍스트 엔지니어링으로, 다시 하네스 엔지니어링으로 옮겨 갔습니다. 질문을 잘 쓰는 것만으로는 프로젝트마다 다른 코드 규칙과 업무 맥락을 전달하기 어려웠고, AI가 만든 코드는 그 자체로 신뢰할 근거가 없었습니다. 그래서 AI 결과를 믿는 대신 통과 조건을 개발 절차에 넣기로 했습니다. AI가 참고할 정보·금지할 패턴·사람이 검토할 항목을 정리한 뒤, 타입 검사·테스트·빌드에 더해 발화 테스트와 LLM 응답 검증, Playwright E2E까지 통과해야만 배포되도록 필수 게이트로 편입했습니다. 발화 테스트와 응답 검증은 일반 CI에는 없는, AI 서비스이기 때문에 필요한 관문입니다. 사람이 매번 판정하지 않아도 같은 기준으로 품질이 걸러지게 만든 것입니다.

## 개인의 방식을 팀의 개발 방식으로 정착시킵니다

이 방식은 제 개인 사용법에 머물지 않았습니다. AI 생성 코드의 컨텍스트 관리·금지 패턴·보안 위험·검증 절차를 프론트엔드 개발 표준으로 정리해 사내 공식 문서로 채택했습니다. 같은 기준을 사람 권한으로 강제하는 대신, 이 표준의 검증 항목을 배포 파이프라인의 게이트로 걸어 두어 다나아데이터 스쿼드 10명이 자연히 같은 기준으로 개발하게 만들었습니다.

세미나와 문서는 이 기준을 팀에 정착시키고 재현 가능하게 만드는 역할을 맡았습니다. 외부 컨퍼런스에서 얻은 인사이트를 개발 세미나 12회로 팀에 이식하고, 검증 기준과 노하우를 기술 문서 48건으로 남겨 새로 합류한 사람도 같은 기준으로 시작하게 했습니다. 반복 작업의 시간을 실제로 줄인 것은 두 가지 장치였습니다. Storybook으로 재사용 컴포넌트를 카탈로그화해 반복 컴포넌트 개발 시간이 90분에서 15분으로(약 83%) 줄었고, 반복 검증을 자동 판정으로 대체해 반복 QA 시간이 3시간에서 30분으로 줄었습니다. 이렇게 확보한 시간을 다시 기능 개발과 코드 검토에 투입했습니다. 새 AI 도구를 접할 때마다 원리를 먼저 확인하고, 실무에서 효과와 한계를 검증한 뒤, 동료가 재현할 수 있는 기준으로 만드는 것이 제가 AI 전환을 이끄는 방식입니다.
