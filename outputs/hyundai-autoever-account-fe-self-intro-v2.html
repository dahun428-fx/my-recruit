항목 1 · 빠른지, 숫자로 증명되는지, 안전한지를 함께 판단합니다

프론트엔드의 품질을 저는 화면이 얼마나 빨리 뜨는지, 그 개선을 숫자로 증명할 수 있는지, 사용자 데이터를 안전하게 다루는지로 판단합니다.

렌더링 전략은 최초 노출과 상호작용 중 어느 쪽 비용이 큰지로 고릅니다. 내담씨앤씨 SI로 참여한 한국미스미 커머스의 React·TypeScript 기반 Next.js 전환에서는 본사가 설계한 구조 위에서, 초기 노출이 중요한 상품·검색 유입 페이지는 SSR로, 로그인 후 상호작용이 많은 페이지는 CSR로 나누는 구현 판단을 맡았고, 이 전환 프로젝트로 기존 PHP 서비스 대비 평균 로딩 속도가 약 50% 개선됐습니다(GA 기준). 삼성물산 현장 앱에서는 수만 건 목록을 FlatList 가상화와 재렌더링 제거로 바꿔 검색 결과 노출 시간을 5초에서 1초로 줄였습니다.

원인은 측정으로 확인합니다. 삼성물산 앱이 느렸을 때 "API 호출이 많아 느릴 것"이라는 추정 대신 API 응답 시간과 검색 결과가 화면에 노출되는 시점을 나눠 재서, 병목이 클라이언트 렌더링에 있음을 확인한 뒤에야 목록 렌더링을 고쳤습니다. 개선 결과도 같은 지표로 다시 잽니다. 대웅제약에서는 HTTP/2 전환과 캐시 최적화로 LCP를 2.6초에서 1.5초로 낮췄습니다.

보안은 화면에 무엇을 그리고 토큰을 어디에 두는지에서 결정된다고 봅니다. AI 건강검진 챗봇에서는 LLM이 만든 Markdown을 HTML 문자열로 주입하지 않고, rehype-sanitize로 필터링한 뒤 표·목록·링크·차트만 허용된 React 컴포넌트로 매핑해 렌더링하는 전용 계층을 직접 설계했습니다. 고객사 사내 통합 로그인(SSO)과 연동하는 OAuth 2.0 작업은 두 SI 프로젝트(삼성물산·한국미스미)에 걸쳐 프론트엔드를 맡아, Authorization Code 흐름의 콜백을 처리하고 토큰 만료를 감지하면 리프레시 후 요청을 재시도하며 갱신에 실패하면 재로그인으로 보내는 인터셉터를 구현했습니다. 그중 한국미스미 웹에서는 콜백의 state를 검증해 CSRF를 막고, Access 토큰은 메모리에, Refresh 토큰은 서버가 설정하는 httpOnly 쿠키에 두도록 연동해 XSS 노출을 줄였습니다. AI 생성 코드가 늘어난 뒤에는 금지 패턴과 비밀키 노출을 코드 편집 단계에서 자동 점검하도록 했습니다.

항목 2 · 맡겨진 레거시에서 출발해, 다음 기술로 가는 길을 스스로 냈습니다

내담씨앤씨에서 SI로 처음 투입된 곳은 PHP·jQuery로 운영되던 한국미스미 글로벌 B2B 커머스였습니다. 프로젝트 배정은 회사가 정하지만, 어떤 기술로 일할 수 있는 개발자가 될지는 제가 준비할 수 있다고 생각했습니다. Vue·React 같은 SPA 기술을 꾸준히 학습하고 그 역량을 어필해 일본 본사 주도의 Next.js 전면 전환에 투입됐습니다.

전환에서는 한국 팀 6명 중 React 경험이 가장 많은 개발자로서 마이그레이션을 실질적으로 이끌었고, 일본 본사 개발자와 일본어로 요구사항과 설계를 직접 조율해 한국 웹의 전면 전환을 마쳤습니다. 전체 아키텍처는 본사가 설계했기에, 그 구조를 한국 서비스의 요구에 맞게 옮기는 판단이 제 몫이었습니다. 이후에는 Vue 3·Vuex 대시보드와 React Native 앱을 Spring REST API와 연동해 개발하는 삼성물산 프로젝트로 이어졌습니다.

SI에서 기술 스택을 정할 권한은 없었습니다. 스택은 고객이 정했지만, 상태를 어디에 둘지와 데이터를 어디서 거를지는 제가 정했습니다. 삼성물산 앱에서는 서버 상태는 React Query, 화면 상태는 로컬, 여러 화면이 공유하는 값만 Recoil 전역으로 두었고, 데이터 규모를 기준으로 클라이언트 필터링과 서버 검색의 경계를 나눴습니다.

GPT-4o가 등장한 무렵에는 AI 기술을 익혀야 한다고 느껴 LangChain·RAG 같은 LLM 기술을 스스로 공부했고, 이후 AI 제품을 만드는 조직으로 옮기기로 해 대웅제약 AI추진팀에 합류했습니다. 그곳에서 AI 건강검진 챗봇의 프론트엔드를 총괄해 임직원 3,493명이 실사용한 서비스로 출시했습니다. AI가 만든 코드를 같은 기준으로 걸러 내는 검증 하네스를 구축하고 FE AX 개발 표준을 설계했으며, GitLab MR 리뷰로 그 기준을 함께 확인하며 이 방식을 10명 팀 전원의 개발 방식으로 정착시켰습니다.

항목 3 · 더 많은 사용자가 처음 만나는 화면을, 더 큰 팀의 표준으로 만들고 싶습니다

제가 다뤄 온 서비스 중 가장 큰 규모는 월 방문자 약 112만(GA·Adobe Analytics 기준)의 B2B 커머스였습니다. 더 큰 규모를 원하는 이유는 측정에 있습니다. 사용자가 많을수록 작은 성능 개선도 수많은 로그인과 화면 전환으로 바로 드러나, 개선의 효과를 분명한 숫자로 확인할 수 있습니다.

플레오스 2.0에서 현대자동차·기아·제네시스 브랜드 서비스로 들어가는 입구가 되는 것이 계정·인증 화면이라고 생각합니다. 로그인 지연이나 토큰 만료 처리의 작은 어긋남은 그 뒤의 서비스 경험 전체로 번집니다. 두 SI 프로젝트에서 사내 통합 로그인(SSO)과 OAuth 2.0을 연동해 온 경험이 바로 닿는 자리이기도 해서, 계정 시스템 프론트엔드에서 더 큰 규모의 성능과 안정성을 책임지고 싶어 지원했습니다.

또 하나는 디자인 시스템과 표준입니다. AI코치에서는 기능별 차등 가격 요구를 화면 커스터마이징이 아니라 Config-Driven 기능 노출 제어로 풀기로 하고, 이미 완성된 코드의 대규모 리팩토링을 감수했습니다. 비즈36.5·AI코치·바이오에이지 3개 서비스에서는 변경 이유가 같은 UI만 공통 컴포넌트로 올리고 고객사별 차이는 Base-Theme 설정과 로고·컬러 토큰으로 분리했으며, Storybook으로 기획자와 UI를 조기 확정해 기획–개발 검증 리드타임을 2일에서 1일로 줄였습니다. 다만 이것은 한 팀, 세 서비스에서 검증한 공통 컴포넌트 구조였고, 더 큰 조직으로 넓히는 것이 다음 과제입니다.

품질 기준은 도구로 지켰습니다. Playwright E2E를 배포의 필수 Gate로 두어 담당자가 없어도 같은 기준으로 검증·배포되게 했고, 배포 전 사전검증·배포 후 Smoke Test·Rollback을 정해진 순서로 실행하는 Release Flow를 팀의 표준 Toolchain으로 운영했습니다. FE엔지니어링팀이 디자인 시스템과 기술 Governance·표준 Toolchain을 함께 다루는 만큼, 이 공통화와 표준 운영 경험을 더 큰 조직의 디자인 시스템과 표준으로 키우는 일에 참여하고 싶습니다. 입사 후에는 먼저 로그인·토큰 갱신 구간의 실패율과 소요 시간을 계측해 기준선을 만들고, 그 숫자를 기준으로 개선 순서를 정하겠습니다.
