# Process Rules (작업 방식 규칙 대장)

소유자가 AI의 **작업 방식**(결과 보고, 절차, 위임, 확인 요청)에 준 피드백을
일반화해 축적하는 대장이다. 산출물(글)의 품질 선호는
`docs/resume-reference/feedback-rules.md`가 정본이며, 이 대장은 "AI가 어떻게
일하는가"만 담는다. 이 파일은 `CLAUDE.md`가 @import 하므로 여기 실린 내용은
매 세션 컨텍스트에 상주한다 — 간결함이 곧 비용이다.

## 운영 규칙

- **적용 대상**: 모든 에이전트(Claude·Codex 포함) 공유. active와 probation
  모두 따른다(probation은 잠정이되 적용 대상). Claude 하네스에만 해당하는
  규칙은 `- 범위: Claude` 필드로 표시한다. 최상위 에이전트는 서브에이전트에
  위임할 때 그 작업과 관련된 active/probation 규칙을 프롬프트에 요약해
  전달한다.
- **수집**: 일회성 지시("이번엔 짧게 보고해")는 규칙화하지 않는다.
  "앞으로는/항상/매번" 같은 지속성 어휘가 있으면 즉시 후보를 한 줄로
  제안한다. 지속성 어휘 없는 교정은 하단 "관찰 로그"에 한 줄로 남기고, 같은
  교정이 2회째 관찰될 때 후보로 제안한다. 규칙은 소유자가 승인한 것만
  기록한다. 무단 규칙 기록 금지.
- **상태 모델**: 강도 `MUST` / `NEVER` / `PREFER`(어길 땐 이유 명시). 상태
  `probation` / `active` / `retired`. 새 규칙은 `probation`으로 시작한다.
  - "적용 1회" = 규칙의 트리거 상황이 실제 발생했고 재교정 없이 통과한 것.
    세션당 규칙별 최대 1회만 집계하며 `- 적용: YYYY-MM-DD ✓ 무엇으로 확인`
    형식으로 남긴다. 세션의 마지막 응답에서만 발휘된 적용은 소유자가 교정할
    기회가 없었으므로 그 자리에서 집계하지 않고, 다음 세션에서 무교정을
    확인한 뒤 집계한다. ✓ 2회는 승격 가능 시점 표시일 뿐이며, `active`
    승격은 에이전트가 제안하지 않고 소유자가 실제 활용 판단으로 지시한다.
  - 재교정이 오면 성격을 구분한다. **위반**(규칙은 유효한데 에이전트가
    어김) → 규칙은 유지하고 `- 적용: YYYY-MM-DD 위반(요지)`을 기록하며,
    반복 위반 + 기계 검사 가능이면 hook 승격 후보로 올린다.
    **선호 변경**(소유자가 규칙 자체를 뒤집음) → 수정 또는 retire를
    제안한다.
  - 상태 전이는 전부 승인제. **삭제는 없다** — retire 시 헤딩 상태를
    `retired`로 바꾸고 `- 해제: YYYY-MM-DD 이유`를 붙여
    `process-rules-archive.md`로 옮긴다(아카이브는 컨텍스트에 상주하지
    않는다).
- **일반화 우선**: 새 규칙 추가보다 기존 규칙을 일반화해 갱신하는 것이 기본
  동작이다. 추가 시 기존 규칙과의 모순을 검사하고, 충돌하면 어느 쪽이 최신
  취향인지 물어 한쪽을 retire한다.
- **소프트 캡**: active 15개, probation 5개. 추가·승격 시점 모두 캡을
  검사하고, 초과하면 통합·정리 후보를 함께 제안한다.
- **강제 지점**: 규칙은 컨텍스트 상주로 상시 적용하고, 실질적 작업 마무리
  보고 시점에 active/probation 규칙 위반이 없었는지 자가점검한다.
  자가점검에서 위반을 발견하면 최종 응답 전에 고치고, 고칠 수 없으면 위반
  사실을 보고하며 `- 적용: YYYY-MM-DD 위반(요지)`으로 기록한다. 특정 규칙이
  active인데도 반복 위반되고 기계적으로 검사 가능할 때만, 개별적으로
  settings.json hook 승격을 제안한다(`update-config` 스킬 사용).
- **기록 주체**: 규칙 문장·강도·상태의 신설과 변경은 소유자 승인 후 최상위
  에이전트만 수행한다. `적용:` 이력과 관찰 로그는 운영 메타데이터로, 최상위
  에이전트가 승인 없이 기록할 수 있다. 서브에이전트는 이 파일을 편집하지
  않는다.

## 규칙 형식

카테고리: `보고`(결과 전달 방식) / `절차`(작업 순서·확인 타이밍) /
`위임`(서브에이전트·도구 사용) / `확인`(질문·승인 요청 기준).
카테고리 신설은 소유자 승인 필수. ID는 카테고리와 무관한 `P-NN` 순번이며
재사용하지 않는다 — 새 ID를 매기기 전에 아카이브의 마지막 번호까지
확인한다.

```markdown
### P-NN · 보고 · MUST · probation
규칙 문장 한 줄 (일반화된 형태).
- 출처: YYYY-MM-DD 어떤 세션에서
- 적용: YYYY-MM-DD ✓ 무엇으로 확인   (✓ 2회 → 승격 가능, 소유자 지시)
- 범위: Claude                        (선택, 없으면 모든 에이전트)
```

## 관찰 로그 (규칙 후보 전 단계)

지속성 어휘 없이 온 프로세스 교정을 `- YYYY-MM-DD 교정 요지` 한 줄로
기록한다(승인 불요). 같은 교정이 2회째 보이면 규칙 후보로 제안한다. 규칙이
아니므로 삭제 가능하다 — 규칙화됐거나 60일이 지난 항목은 지운다.

- 2026-07-22 게이트 블로커 해소 시 검증된 성과(Lighthouse 91점)를 제거로 처리 — 스코프 병기로 살리는 쪽을 먼저 시도했어야. 소유자 "왜 뺐니" 교정으로 복원.
- 2026-07-23 헤드헌터 인터뷰 질문을 구조화된 번호 목록으로 제시 → 소유자 "문장형으로 다시 줄래" 교정. 이후 질문은 문장형(prose)으로 전달. (2회째 관찰 시 보고 규칙 후보 제안)
- 2026-07-27 P-01 점수 게이트·P-03 3자 자문 생략 지시("4,5,7 부분은 필요없어") — 일회성으로 처리, 규칙 자체는 유지. 지속성 어휘 없음.
- 2026-07-27 검증 에이전트(적대 검증·reviewer) 지적을 소유자 승인 없이 문면에 반영해 20여 곳을 고쳤다가 "다 내가 적은 기준으로 맞춰, 변경하지말고" 교정으로 전면 되돌림. 앞으로 크리틱 결과는 수용/기각 분류만 제시하고 소유자 판단 후 반영한다. (2회째 관찰 시 절차 규칙 후보 제안)
